# 三阶段场景交接与返工

来源：2026-09-16用户要求“这个都改一下”，明确补齐地形依赖、实例数量、失败回流。以下为制作流程契约，不是飞书原文。背景及Stage 1成品4096×4096，人物有效高度基准H=128；不自动应用历史0.64。

## 一份计划贯穿三阶段

每个Stage 1候选配一份 `candidate-A.scene-plan.json`（B/C同理）。生成前先规划，成品标准化后绑定实际文件SHA-256并核对可见原型；运行脚本验证后才能把它称为可交接候选。单张外部图没有计划时，由Stage 2执行者按本次图补写，不能退回“每种一次”并声称恢复场景。

`scene-plan.v1`包含：
- `source_sha256`：选定Stage 1原图的文件哈希；`canvas:[4096,4096]`、`H_px:128`。
- `density:{intent,basis}`：目标疏密、分组和空隙意图，以及用户需求或可见参考依据；不是单纯填满率。
- `goals:[{id,description}]`：最终必须目视满足的场景目标，如可辨认的小镇中心、铁路与车站关系；至少一项。
- `infrastructure:[{kind,description}]`：保留的`rail/water/road/bridge/platform`及可见位置、宽度和连通意图。铁路是功能地形，不能按railings、围栏或装饰压边删除。
- `assets:[{id,count,count_basis,critical,class,role,zones,requires}]`：稳定原型ID、**实例数量**、数量依据、核心物件标记、Layout类别、target/distractor、合法地形和基础设施依赖。至少一个critical。`count_basis`为`{mode:user|observed|authored,reason:具体依据}`；authored代表执行者明确设计，不冒充用户指定或原图实测。

原型种类与实例数量分开。用户明确数量优先；否则先观察重复密度、按可用地形编制明确的数量方案并告知假设，不静默每种一次、不机械照搬测试集数量。纯素材请求也可形成供下游采用的authored建议计划，但不启动Layout。三消等整组数量仅在明确玩法时使用；不从主题自动猜玩法。

原型ID使用英文字母数字、点、横线或下划线。class用Layout真实类别，如building/person/land_animal/vehicle/rail_vehicle/boat/prop。火车class=rail_vehicle、requires含rail；船class=boat、requires含water；陆车class=vehicle、requires含road。requires可为空但必须显式填写。zones使用Harness地形词汇，只能在其底层合法规则内收窄。背景的道路、水域及铁路必须能容纳计划资产，不能只画一个象征性小色块。

Stage 2默认选择22种原型（建筑8、道具6、载具3、角色5；用户明确覆盖优先）时，沿用对应稳定ID。候选计划与选材不一致须形成可追溯修订，说明合并/剔除原因；核心物件不能悄悄删除。交接包中的计划必须恰好覆盖所有实际非背景原型。

## 只验证有证据的结论

- 基础设施人工复核绑定背景与计划哈希；检查位置、连续性、桥头接岸、宽度和承载关系。PNG存在不表示基础设施存在。
- Layout用实际语义mask检查必需地形类是否存在，用已有capacity-preflight测可容纳数量。缺地形先对照背景，区分漏标与背景本身缺失；单次预检不足不冒称全局无解。
- 三个seed共享同一份计划、数量、尺寸、背景和mask。交接包更换后必须重开项目/seed批次。
- 最终数量逐原型对照scene-plan，**countTolerance不能覆盖交接计划的缺项**。核心物件缺失特别指出；非核心缺项也不能称原计划完整完成。
- 最终render还须核对density与全部goals，并绑定layout、render、mask、plan的哈希。美术合格、几何合法、场景目标完成分别记录。这个闭环不代表已验证碰撞玩法、点击难度或游戏可玩性。

## 返工路由与停止条件

Layout写出`repair-request.json`并保存历史版本，包含阶段、输入指纹、失败对象/数量及建议路由。

| 证据 | 修正去向 |
|---|---|
| mask与真实背景不符，或rules误判 | Layout修正mask/rules，重做相关预检 |
| 原型校准或背景尺寸错误 | Stage 2尺度校准；不以“缩到能放下”为依据 |
| 已选火车却无轨道，或真实地块被删/被装饰挤占 | Stage 2背景定向修正，保留原有主题与必要结构 |
| 尺度、mask、规则正确，仍无法装入实例计划 | 先检查Layout地块分配；再提出背景容量修正或有依据的Stage 1计划修订 |
| 密度、核心组合或视觉目标未通过 | Layout调整布局；需要新增原型或改变主题方案时回Stage 1/2 |

用户已经请求整条流程时，在授权范围内自动走对应修复步骤，不重复询问例行修正。仅请求独立阶段时，交付该阶段结果及内部返工记录，不擅自启动新阶段。不得擅改明确数量、核心内容或用提高容差消除问题；用户明确选择减量时创建新计划修订并保留原目标未完成的事实。

每次请求最多两轮定向返工，继承各图像槽位已有重试预算；用新运行目录和supersedes说明保存新旧关系。未解决则直接交付实际已生成的PNG，在最终输出说明问题，不弹出候选或验收，不能循环无限重生或自动填写通过。背景/素材变化使对应人工复核失效，重新校准、验收、生成交接包，再从预检开始。

## 新主题数量默认值

新计划读取[实例数量规则](scene-count-policy.md)，填写count_policy：默认216、下限201，逐原型合计必须等于目标；按具体原型与地形编制，不直接照搬案例比例。历史计划不追溯修改；用户明确覆盖保留原话。三阶段继承同一政策和总目标，容量不足不得以countTolerance降低目标。
