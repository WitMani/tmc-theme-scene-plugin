# 生图前的布局草图

每个主题先完成 A/B/C 三张布局草图并审核，再开始该主题的成品生图。草图是必须保存、实际查看的图片，不以文字方案代替。仅修改插件或讨论流程时不触发生成。

## 分工与输入

主 agent 查看参考组，确定主题元素、交互用途假设、输出画幅和共同正交镜头，将这些资料及参考图片路径交给布局设计 subagent。有多 agent 工具时实际委派，等待其交付；不另建用户侧任务。subagent 负责布局与草图，不自行生成最终场景或修改插件。工具不可用时由主 agent 按相同步骤完成，明确记录未使用独立 subagent。

## 草图交付

1. 为 A/B/C 分别规划点击区、非点击区、道路/水路与主要物件群，保留均衡分布、局部聚集、分区串联的实质差异。先分配宽裕的点击区，再安排少量环境点缀；三张保持同一画幅、镜头及资产尺度。
2. 用简单 SVG 多边形、线条和物件占位轮廓绘制原创示意图，渲染为 PNG；此步骤是新建布局图，不编辑参考图，不需要额外生图调用。草图以共同斜俯视正交方向表达地块与简化体块，不混用顶视图和透视镜头。优先用本地可用矢量渲染工具，不为草图转用外部 API。
3. 用少量示意色区分点击区和非点击区；道路/水域的交互用途另行注明，避免把所有水面都判为非点击区。标注主要物件群占位、桥接岸、连接关系与必要间距。图内可用简短区域 ID；颜色图例、ID 对应元素和用途写入配套说明。示意色不代表成品配色。
4. 每张保存 `layout-A.svg`、`layout-A.png`、`layout-A.json`（B/C同理）。JSON至少包含 candidate_id、画布尺寸、共同镜头说明、区域ID/多边形/交互用途/地表类型、物件群占位、连接关系、用途假设及设计说明。空间坐标是规划数据，不是从参考图测得，也不是运行时碰撞或点击数据。

## 草图审核

主 agent 或另一个审核 subagent 必须实际查看三张 PNG，结合 JSON 检查：点击区明显为主；非点击地形少量且未挤占中央；地块能容纳规划物件并留出间距；道路/水路和桥接岸合理；镜头一致；A/B/C空间方案不同。审核记录具体区域与问题，不仅复述设计意图，不捏造面积测量。

有明显问题时交回设计者修正，默认最多两轮草图修订并保留版本。仍有阻碍时标记未通过，不进入该主题成品生图，不将草图计为已完成候选。默认这是 agent 内部审核；审核通过后展示草图或提供链接并继续，不额外等待用户批准。用户明确要求先看草图或确认后再生图时，按其要求暂停。

## 成品参考与检查

每次生图输入顺序：完整干净参考组 N 张 → 共用正交辅助线图 1 张（启用时）→ 当前候选已审核的布局草图 1 张。默认共 N+2 张，即3–5张。每次只传当前候选草图，不能把三张都传入或把A草图用于B/C。关闭辅助线时共N+1张。

干净图负责画风、比例和细节；辅助线负责投影方向；布局草图负责地块、空间占比、物件群和连接关系。明确提示生成器忽略草图的示意颜色、标签、轮廓框与图例，不复制原图布局。草图和辅助线均是软约束；最后逐张对照草图检查点击空间是否被环境内容侵占、连接是否丢失、有无示意标记残留。明显偏差沿用每候选最多一次成品修正上限。

所有输入有本地路径时用文件引用参数；涉及近期图片机制时必须确认完整参考组、辅助线和当前草图都能被纳入工具上限，不静默省略原图或草图，不拼图绕过限制。无法完整引用时说明缺失项并请求重附所需图片。

manifest 每个候选增加 layout_sketch：SVG/PNG/JSON路径、设计者实际角色、审核者实际角色、状态、修订次数、审核记录、最终采用版本。记录实际输入图片顺序。交付时同时链接草图及对应成品，说明实际观察到的偏差；草图不计入3T张成品数量。
